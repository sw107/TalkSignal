# 알림 DB 방식 검증용 앱

기존 TalkSignal의 동작을 바꾸기 전에, 카카오톡 창과 알림 센터 패널이 닫힌 상태에서 수신 알림 기록을 조회할 수 있는지 확인하기 위한 별도 앱입니다. 기존 메뉴바 앱에 DB 기능을 추가한 버전은 아닙니다.

```sh
./scripts/build-db-check.sh '확인할 발신자 이름'
open build/TalkSignalDBCheck.app
```

`시스템 설정 → 개인정보 보호 및 보안 → 전체 디스크 접근`에서 **TalkSignal DB Check**를 추가해 허용합니다. macOS가 요청하면 앱을 종료 후 다시 실행합니다. 접근성 권한을 가진 터미널이나 Codex에 광범위한 디스크 권한을 주는 대신, 이 별도 앱에 권한을 줄 수 있습니다.

## 검사 범위

- 알림 DB를 `SQLITE_OPEN_READONLY`와 `PRAGMA query_only`로 열어 카카오톡의 최근 기록만 조회합니다.
- 알림 제목/부제목이 입력한 발신자 이름과 정확히 일치하는지 검사합니다.
- 직렬화된 알림 레코드에는 본문도 포함되지만, 본문 필드는 판별에 사용하거나 표시·저장하지 않습니다.
- DB 파일을 복사하거나 외부로 전송하지 않습니다. 네트워크 코드는 없습니다.
- 최초 성공한 조회의 기록 ID를 기준으로 새로 발견한 일치 알림을 따로 셉니다.
- `build/dbcheck-result.json`에 검사 시각, 일치 여부를 나타내는 기록 ID, 알림 시각, 창 메타데이터 등을 저장합니다. 원인 진단을 위해 카톡 알림 제목·부제목도 기록하므로 발신자/채팅방 이름이 포함될 수 있습니다. 메시지 본문과 사용자 데이터 값은 출력·저장하지 않습니다. 두 번째 빌드 인자로 결과 파일 위치를 바꿀 수 있습니다. 결과 파일을 Git에 추가하지 마세요.
- 이 앱에 주는 전체 디스크 접근 권한 자체는 카카오톡에만 한정된 권한이 아닙니다. 검사 후 앱을 종료하고 권한을 제거할 수 있습니다.

## 해석상의 한계

알림 DB는 macOS 내부 구현이며 공개 수신 API가 아닙니다. 구조가 예상과 다르거나 읽기가 실패하면 실패 상태를 표시합니다. 알림 DB의 수신 기록은 카카오톡의 실제 읽음 상태를 증명하지 않습니다.

`notificationCenterOnScreenWindows`에는 알림 센터 프로세스가 관리하는 다른 윈도우/위젯도 포함될 수 있습니다. 이 숫자만으로 패널의 열림·닫힘을 판정하지 말고, 별도 접근성 창 메타데이터와 사용자가 확인한 상태를 함께 사용해야 합니다.

초기 구현은 새 기록 ID를 기준으로 합니다. macOS가 같은 기록을 덮어쓰는 경우, 그룹화/삭제·다른 기기에서 읽음 처리 등은 추가 검증이 필요합니다.

## 2026-10-23 로컬 확인 결과

- 별도 검사 앱의 전체 디스크 접근 허용 후 DB 읽기와 예상 스키마 조회에 성공했습니다.
- 카카오톡 접근성 창은 0개였습니다. 알림 센터 프로세스의 3개 창은 위젯이었으며, 알림 센터 패널은 없었습니다. 검사 중 두 앱의 창을 열지 않았습니다.
- 해당 시점의 카카오톡 알림 조회 결과는 0건이었습니다. 새 테스트 메시지를 받을 수 없어 발신자 매칭 및 두 창이 닫힌 상태의 신규 수신 감지는 아직 검증하지 못했습니다.
- DB 접근 성공만으로 알림 감지 기능이 검증된 것은 아닙니다. 기존 TalkSignal 앱의 감지 방식은 변경하지 않았습니다.

### 0건 조회 원인 확인 및 수정

추가 진단에서 카카오톡 알림 기록 2건이 존재하며, DB의 앱 식별자가 `com.kakao.kakaotalkmac`으로 소문자 저장된 것을 확인했습니다. 초기 코드는 `com.kakao.KakaoTalkMac`을 대소문자 구분 비교하여 0건을 반환했습니다. 조회에 `COLLATE NOCASE`를 추가했습니다. 메모리 내 SQLite 재현 테스트에서 기존 조건은 0건, 수정 조건은 카톡 2건만 반환하고 다른 앱의 기록은 제외하는 것을 확인했습니다. 앞의 0건 결과는 알림 부재의 증거가 아닙니다.

수정 앱의 실제 발신자 매칭은 별도로 확인해야 합니다. 임시 서명으로 앱을 다시 빌드하면 전체 디스크 접근을 재등록해야 할 수 있습니다.

### 기존 알림의 발신자 매칭 확인

수정본에서 실제 카톡 알림의 제목은 단체방 이름이 아닌 발신자 이름으로 저장된 것을 확인했습니다. 사용자가 해당 메시지가 지정한 단체방에서 왔다고 확인했습니다. 검사 대상을 그 발신자 이름으로 바꾸자 기존 알림이 일치했고, 앱 UI에도 발신자의 알림을 찾았다고 표시됐습니다. 이때 카카오톡 AX 창은 0개, 알림 센터 AX 창은 위젯 3개뿐이었으며 두 창을 열지 않았습니다.

이는 두 창이 닫힌 상태에서 **기존 알림을 발신자 기준으로 조회하는 동작**의 검증입니다. 대상 변경 이후 새 일치 알림 수는 0개였으며, 새로운 메시지 도착의 실시간 감지와 카카오톡 실제 안 읽음 상태는 별도 검증 대상입니다. 단체방 이름으로 감지하려면 추가 식별 정보가 필요합니다.

### 휴대폰에서 읽은 뒤 비교

사용자가 휴대폰에서 해당 단체방 메시지를 읽었다고 확인한 전후를 비교했습니다. 검사 도중 카카오톡 창과 알림 센터 패널을 열지 않았으며, 접근성 창 메타데이터에서도 카카오톡 창 0개와 알림 센터의 위젯만 확인했습니다.

읽기 전 일치 알림 2건은 사용자 확인 후 첫 조회와 추가 대기 후 조회에서도 같은 기록 ID 및 수신 시각으로 남았습니다. 첫 사후 조회와 마지막 조회 사이에는 약 1분이 경과했습니다. 현재 코드가 관찰하는 알림 존재 여부/ID/수신 시각으로는 이번 휴대폰 읽음 처리를 감지하지 못했습니다. 따라서 알림 존재를 실제 안 읽음 상태로 표시하거나, 알림 삭제를 확정적인 읽음으로 처리해서는 안 됩니다. 모든 내부 필드가 불변이라는 의미는 아니며, 읽음 전후의 카톡 자체 상태를 닫힌 창에서 직접 검증한 것도 아닙니다.
